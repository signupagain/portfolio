您好，我是**王宗彥**，一名前端工程師，專注於 Vue 與 Nuxt 生態系開發。雖非本科但基於個人傾向開始積極學習前端。逐步建立從 UI 實作到資料流與架構拆分的完整開發能力，把抽象架構成功落地。

## 技術選型與專案策略

初期專案，會依據設計稿的整體 UI、目標群體及產品性質，評估**開發效率**、**維護成本**與**專案生命週期**決定技術選型。比如：偏向品牌頁，我會傾向儘可能少的依賴，保持輕量和靈活；而偏向功能性較重的專案，我會選擇組件富足的庫來加速開發。讓專案複雜度依其實際需求而定，避免過度設計，確保**開發時程的精準掌控與長期維護的低成本化**。

## 模組化與可複用設計

這份作品集本身即為架構實踐：以 **Nuxt Layers** 將自我介紹、圖庫、檔案瀏覽器等拆成可獨立維護的子專案，共用元件（如主題切換、快捷操作）則抽成可複用 layer，依需求透過 `extends` 組合注入。這樣複雜度隨功能增長而擴展，而非一開始就把所有邏輯耦合在同一個 app 裡。

## 內容管理與渲染策略

靜態內容我以 **Nuxt Content** 管理，並以 Zod 為每個 collection 定義 schema，讓 Markdown / YAML 在 build 時就完成驗證，避免內容結構錯誤拖到 runtime 才發現。靜態介紹頁採預渲染以優化首屏與 SEO；需即時資料的頁面則在伺服器預取後再 hydrate。

## API 契約與型別安全

在 API 請求的部份，我會用 **Zod** 定義 Schema，並以 **oRPC** 建立前後端契約：伺服器端保留完整回應型別，客戶端只暴露必要欄位，型別從契約一路推到 composable。敏感憑證走 Server API 代理，不暴露於前端，確保開發的**安全性**及接口的**一致性**。這樣不僅能減少溝通成本，還能在開發過程中及早發現問題，提升整體開發效率。

## 狀態管理與資料流設計

狀態管理方面，我依**資料性質**選擇工具，而非套用單一方案。複雜 UI 互動與本地狀態（如多選、排序、框選）適合用 **Pinia** 集中管理；遠端資料、快取與 SSR 預取則交給 **Vue Query**，搭配 `onServerPrefetch` 優化首屏渲染。兩者分工明確，避免把所有狀態塞進同一個 store。

同時，我會根據內容建立資料流，釐清組件間的依賴關係，將 UI 互動與狀態邏輯分層管理，確保資料流向清晰。組件內部保持單一職責，讓 UI 的變化不會影響資料的處理邏輯，反之亦然。

## 效能與大量資料 UI

面對大量 DOM 或大量資料，我會從渲染策略下手：**虛擬滾動**只渲染可視區、**事件委派**降低監聽成本、**漸進式載入**避免首屏阻塞，並搭配 Lazy hydration 與 Skeleton 改善感知速度。圖片則以模糊占位先行、大圖就緒後替換，配合 `@nuxt/image` 做 CDN 優化。這些在圖庫與檔案瀏覽器兩個 demo 中都有實際驗證。

## 測試與品質保障

我採 layer 級 **Vitest** 專案，針對工具函式與 composable 撰寫單元測試，讓關鍵邏輯（如 LRU 搜尋紀錄、View Transition 降級）在迭代中可重複驗證，而非只靠手動點擊。

## AI 開發

除了傳統開發流程，我也將 **AI 輔助工具** 納入日常實踐，但定位是「加速器」而非取代思考。我會透過 Cursor **Rules** 與 **Skills** 建立專案級脈絡：限定技術棧、import 規範、格式化與 commit 慣例，讓 AI 產出更貼近 repo 既有風格。搭配 **graphify** 知識圖譜理解跨檔案依賴，縮短在 Nuxt Layers 結構中的定位時間。

實務上，我讓 AI 負責 boilerplate、重構草稿與測試骨架，但架構拆分、API 契約與效能策略等關鍵決策仍由人工把關；產出必須通過型別檢查、lint 與 Vitest，避免「能跑但不對」的程式碼進入 codebase。這樣能在保持品質的前提下，把時間集中在 UI 互動、資料流與邊界條件等更需要判斷力的環節。

## 開發理念與持續成長

總的來說，我在前端開發中會關注資料流向並分層管理，致力於打造可持續迭代的 Web 應用。每個抽象原則都力求在程式碼裡找到對應的落地證據。且在多變的前端生態中，保持學習和適應新技術的能力，持續提升自己的專業技能。
